# Mob Presentation

Make the presentation help its audience understand or decide. Choose the smallest workflow that can meet the request. This skill supplies decisions and quality criteria; the selected host tool supplies execution.

## Start with the audience and value

First help the creator state who the presentation is for, what value it offers that audience and what they should do after viewing it. Read the request and supplied material, infer and state a concise working interpretation, and reuse existing answers. Ask briefly only about a material unknown; do not turn this into a form or repeated confirmation. For a bounded edit, reuse the existing framing unless the change affects it. See [content](references/content.md) for the framing method.

Identify the requested change, intended use, output destination, source facts, editable elements, template constraints and material limits. Read the exact current artifact when supplied. See the [input and output contract](references/contract.md) when an application or project supplies these inputs.

Use caller-provided facts, brand assets and decisions through their authorized references. The skill contains no company knowledge or default brand. A previous slide proves what was written, not whether its claim is true.

## Core production flow

For creation or narrative rebuild: audience/value/action → [deck's core claim → page points](references/content.md#core-claim-and-page-points) → [real visual sample](references/quality.md#work-on-a-visible-problem) → authoring → [rendered communication review](references/quality.md#inspect-compare-revise). Develop one [working spec](references/contract.md#working-specification) alongside these decisions; do not freeze layouts before exploring actual content. Reuse valid decisions and samples, and update affected outputs when the argument or design changes. Retain separate content, truthfulness, visual and engineering checks.

## Route the work

| Request | Read only what is needed | Result |
| --- | --- | --- |
| Explain or review a deck | [Content](references/content.md), relevant parts of [quality](references/quality.md) | Findings with page evidence; no unsolicited rewrite |
| Correct a word, number or object | [Tools](references/tools.md), affected checks in quality | Bounded edit through the original capable path; preserve unrelated objects |
| Rebuild narrative or create a new deck | Core production flow above | Working framing and spec, editable artifact and communication review of actual renders |
| Follow an existing template | Template route in tools | Inherited masters/layouts and verified content mapping |
| Explore visuals or improve design | Visual work in quality, then tools | A focused hypothesis and an actual representative result |
| Export or deliver | Tools and quality | Exact final file, evidence of checks and remaining use limitations |
| Capture a reusable lesson | Learning in quality | Scoped observation for its existing owner; no automatic rule promotion |

If a local correction changes a conclusion, source, maturity claim or narrative dependency, reopen that affected decision. Do not use a layout edit to silently rewrite meaning. For a structural rewrite of an existing deck, account for each source page and the destination of necessary content before removing it.

## Choose one authoring owner

Use the user's explicit tool and destination when available. Otherwise favor a route that preserves the existing source and required editability. [Tool routing](references/tools.md) distinguishes host presentation tools, PPT Master, native OOXML, HTML/SVG, and image generation. Verify availability and read the selected tool's current entry before using it. A tool name or a Markdown instruction does not install a capability.

Keep visual exploration and image sourcing separate from the authoring owner. A concept image may express an idea; it cannot verify a product, customer, deployment or measured result. Required editable text, tables and data charts must survive as editable objects, not a flattened page image.

## Iterate against evidence

Inspect the actual rendered artifact. Compare the candidate with the requested reference and the current best version under the same reading conditions. Check communication and visual quality separately from technical validity. A clean export or a named template cannot establish that a slide communicates well.

When a candidate misses the stated goal, retain the best version and revise internally within the authorized scope. Change the failing assumption, rather than repeatedly decorating the same failed composition. Record the observed problem and what the next change tests. Continue while permitted and useful; real tool failures, permissions, budget limits or a needed user decision remain stopping conditions. Do not invent a quota or claim unlimited retries.

Full-deck creation needs inspection of every rendered page. A bounded edit needs the affected pages and genuine dependencies; do not claim a fresh whole-deck review. Inspect adjacent slides when the change affects flow. See quality for rendering and editability limits.

## Deliver and learn

Return the requested artifact and material limitations. Keep validation details outside the slides unless the audience needs them. Distinguish a draft, a tool-checked file, an agent recommendation and a user-accepted result. Changed content invalidates the affected previous checks.

Preserve the caller's existing source and review records. Capture only observations supported by an actual comparison, with applicability and uncertainty. A page-specific preference remains local. Publication, installation and project acceptance follow the caller's authority; this skill creates none of them.
